## 1. 项目概览

### 1.1 这是什么

一个 Windows 桌面工具，用 **pywebview 单窗口 + 原生 HTML/JS 界面** 包装三个互相独立的
「刷课核心」，统一管理账号配置、课程选择、题库、更新与日志。它本身不实现任何平台的刷课
协议，职责是**装配、编排、监督**，并把核心的控制台输出翻译成前端能理解的运行状态。

它解决的问题：

1. 三个核心各有自己的配置格式（YAML / INI / TOML）、启动命令与工作目录，用户不该关心这些。
2. 核心是长跑进程，需要可靠地启动、停止（含子进程树）、限时、崩溃收敛与自动关机。
3. 核心更新来源不同（GitHub Release、上游 tag 归档、本地魔改），安全策略必须逐条区分。
4. 用户希望「说一句课程名，就只刷那一门」，于是有了课程目录、单课程覆盖与中文模糊匹配。

### 1.2 四个组成部分

| 组成 | 位置 | 性质 | 更新方式 | 关键约束 |
| --- | --- | --- | --- | --- |
| 统一启动器 | `统一启动器.py`、`src/`、`web/`、`bootstrap.py` | 自研，本仓库主体 | 启动器自更新（GitHub Release + manifest + 外层 cmd 脚本） | 运行中的进程绝不覆盖自己 |
| Autovisor | `Autovisor/` | 自研 Python 核心，**含项目本地适配** | ⚠ 只检查上游版本，**禁止覆盖安装** | 与上游差异需人工合并，见 [更新指南 §3](更新指南.md) |
| Yatori | `Yatori/` | 第三方 Go 二进制（`yatori-go-console.exe`，约 300 MB） | GitHub Release，只接受发布方 SHA-256 | 临时目录切换 + 失败回滚 |
| ZHS | `zhs/` | 第三方源码**零补丁副本**（GPL-3.0），独立 venv 运行 | 上游 tag 归档 + 本地哈希清单 + 备份回滚 | 启动器侧集成代码一律写在 `src/`，不得改 `zhs/` |

ZHS 的「零补丁」约束覆盖 `src/zhs_vendor.py` 的 `SYNC_ENTRIES`，不代表整个 `zhs/`
目录都来自上游；同步范围与上游 `pjm314159/zhs` 保持一致（哈希前做 CRLF→LF
归一化），`scripts/update_zhs.py --check` 与 `tests/test_zhs_vendor.py` 都在守护这条规则。
所有集成逻辑位于 `src/zhs_service.py`、`src/zhs_vendor.py`、`src/zhs_bridge/`。

### 1.4 技术栈与硬性约束

| 项 | 选择 | 约束来源 |
| --- | --- | --- |
| 桌面壳 | `pywebview>=4,<5`（EdgeChromium/WebView2） | `src/dependencies.py`、`requirements.txt` |
| 前端 | 原生 JS + CSS，无框架、无构建步骤 | `web/app.js`、`web/styles.css` |
| 浏览器自动化 | Playwright（Chromium） | Autovisor；`bootstrap.py` 负责安装浏览器 |
| 配置 | `configparser`（INI）、`PyYAML`（YAML）、`tomli-w`（ZHS 的 TOML，在 venv-zhs 内） | 各核心自有格式 |
| 网络 | 标准库 `urllib`（启动器自身）+ `requests`（部分服务） | 避免额外依赖 |
| 题库 | SQLite + `jieba` 分词 | `src/题库服务器.py` |
| 加密 | `pycryptodome` | 核心依赖（Autovisor 登录相关） |
| 并发 | `threading`（无 asyncio、无进程池） | 启动器全同步风格 |
| Python 版本 | 启动器 3.11–3.13；ZHS venv 3.13–3.14 | `bootstrap.py` 的 `MIN_PYTHON` / `ZHS_MIN_PYTHON` |

⚠ 三条不可违反的工程约束：

1. **`src/` 不得 import `统一启动器.py`**。两者只能通过 `src/launcher_api.py` 的注入与
   回调通信，否则测试无法在不启动 WebView 的情况下导入服务。
2. **新增启动器基础依赖时同步声明与检查**：更新 `requirements.txt`、
   `src/dependencies.py` 的 `CORE_DEPENDENCIES` 与相关测试；Dashboard、可选二进制、
   开发依赖分别放入对应清单，ZHS 依赖从上游 `pyproject.toml` 生成，不能全塞进基础依赖。
3. **不在 `zhs/` 的上游同步范围写本地适配，不用上游包覆盖本地 Autovisor**。
   ZHS 集成改 `src/`；Autovisor 自研逻辑可以在 `Autovisor/modules/` 修改并回归。
   `zhs/UPSTREAM.json`、`UPSTREAM.sha256`、`NOTICE.md` 是本地维护的来源元数据，
   不属于上游逐文件一致性比较范围。

### 1.5 版本号体系

项目同时存在多个版本号，含义不同，发布时容易混淆：

| 版本号 | 位置 | 作用 | 谁读取 |
| --- | --- | --- | --- |
| `LAUNCHER_VERSION` | `统一启动器.py:107` | 启动器发布版本，决定自更新是否触发 | `LauncherUpdateService`、`scripts/build_launcher_release.py` |
| `__version__` | `src/version.py` | 产品包版本（关于页显示） | 前端、`get_initial_state` |
| `__build_date__` | `src/version.py` | 构建日期 | 关于页 |
| `.core_versions.json` | 仓库根 | 已安装核心的版本记录（`yatori` / `autovisor` / `zhs` / `last_check`） | `CoreManager` |
| `YATORI_DISPLAY_VERSION` / `AUTOVISOR_DISPLAY_VERSION` | `统一启动器.py:105-106` | 核心未安装时的兜底展示 | 状态快照 |
| `zhs/UPSTREAM.json` → `version` | `zhs/` | ZHS 上游版本 + 来源提交 | `ZhsVendor`、更新弹窗 |

发布 tag（`v1.7.3`）必须与 `LAUNCHER_VERSION` 完全一致，
`build_launcher_release.py --require-version-match` 会强制校验。

### 1.6 术语表

| 术语 | 含义 |
| --- | --- |
| 核心 / core | Yatori、Autovisor、ZHS 三者之一（`script_type` 取值 `yatori` / `autovisor` / `zhs`） |
| runtime / 运行态 | 某核心的子进程正在运行。状态真源是 `launcher.running` 字典 |
| 覆盖（overlay） | 单课程运行前对核心配置做的临时改写，退出时恢复；崩溃后由 `_recover_course_run_overlays` 兜底 |
| 题库服务器 | 进程内 HTTP 服务（默认 `127.0.0.1:8083`），向 Yatori / Autovisor 提供 `/query` |
| 天依 | 内置 AI 助手「洛天依」人格，通过工具调用间接操作启动器 |
| 延迟任务 | 启动后按毫秒延迟执行的 daemon 定时器，见 `ScheduledTaskService` |
| 事务保存 | 同时改写多个配置文件时先快照、失败全部回滚的保存方式 |

### 2.6 结构简洁性与必要性评估（2026-11-13）

结论：**顶层分区合理，服务拆分大多有实际职责；内部依赖与前端集中度仍需改善**。
不建议为了减少文件数，把已有服务重新合并进启动器。评估依据是职责、调用方、独立运行
与发布边界，而非“文件越少越好”。本轮仅调整文档，以下建议尚未实施。

| 结构 | 必要性与现状证据 | 建议 |
| --- | --- | --- |
| `统一启动器.py` + `src/` + `web/` | 桌面装配、可独立测试的后端、静态界面各有职责；`launcher_api.py` 只做桥接 | 保留边界；入口仍有 1970 行，不应描述成只负责组合的极薄入口 |
| `Autovisor/`、`Yatori/`、`zhs/` | 自研 Python、第三方二进制、上游源码副本的配置、依赖和更新策略不同 | 保留三个核心边界；两个 Python 环境是兼容要求，不是重复部署 |
| 进程监督、运行生命周期、批次编排、核心准备 | `ProcessSupervisor` 管输出/终止，`RuntimeProcessService` 管后台生命周期，`RuntimeCoordinator` 管批次完成，`CoreLaunchService` 管核心准备 | 职责不同，保留；修改时明确哪一层拥有启动占位、退出状态与取消逻辑 |

| 更新与依赖模块 | `core_manager.py` 2013 行、`launcher_update_service.py` 1487 行、`zhs_service.py` 1129 行；多个更新策略不能混用 | 暂不做大规模搬迁；优先在变更频繁的领域缩小接口，再考虑内部拆分 |

| `scripts/` | 包含安装、构建、诊断与更新入口；`src/ai_service.py` 还延迟导入 `scripts.ai_connectivity_test` | 不是全都可删除的开发脚本。AI 实现位于脚本层是依赖方向上的待改进点；迁移时保留 CLI 包装并核对发布清单 |
| `data/`、`logs/`、`.runtime/`、`runtime_deps/` | 本地状态、日志、解释器与平台二进制，不能作为冗余源码判断 | 保持与源码分离；删除前先确认进程占用与账号/缓存用途 |

```
┌───────────────────────────────▼──────────────────────────────┐
│ 统一启动器.py  UnifiedLauncher（门面/编排/状态真源）            │
│   惰性 getter：_get_xxx_service()，全部缓存到 self._xxx        │
└───┬───────────┬───────────┬───────────┬───────────┬──────────┘
    │           │           │           │           │
 配置域      进程域      课程域       ZHS 域      题库/更新域

            Runtime     Plan        Vendor      CoreManager
```

依赖方向的唯一例外是回调注入：服务从不 import 启动器，启动器把 `log`、`schedule`、
`on_status_change`、`sync_external_url` 等小函数注入进去。这让服务可以脱离 WebView 单测。

### 3.2 进程模型

| 进程 | 可执行文件 / 命令 | 工作目录 | 生命周期 | 日志去向 |
| --- | --- | --- | --- | --- |
| 启动器主进程 | `.runtime/venv/Scripts/python(w).exe 统一启动器.py` | 仓库根 | 用户关闭 / 自更新 | `logs/` + WebView 日志面板 |
| Yatori | `Yatori/yatori-go-console.exe` 或 `start.bat` | `Yatori/` | `start_yatori` → 退出/超时/停止 | stdout 流式读入 → `logs/yatori` |
| Autovisor | 同主进程解释器 + `Autovisor_Multi.py`/`Autovisor.py` | `Autovisor/` | 同上 | 同上 |
| 练习模式 | 同上 + `Autovisor/Practice_Mode.py` | `Autovisor/` | 独立状态位 `practice` | 同上 |
| ZHS | `.runtime/venv-zhs/Scripts/python.exe -m zhs <action>` | `data/zhs/account-N` | 同上 | 同上，经 `ZhsLogFormatter` 美化 |
| 题库服务器 | **同一进程内的线程**（`ThreadingHTTPServer`） | — | `start_question_bank` / `stop` | 主进程日志 |
| ZHS 扫码桥 | venv-zhs python + `src/zhs_bridge/qr_login.py` | 账号目录 | 一次登录会话 | 写二维码/状态文件或 stdout JSON |
| 自更新脚本 | `cmd /d /s /c .update-staging/应用更新.cmd` | 仓库根 | 与主进程解耦，主进程先退出 | `.update-staging/*.log` |

⚠ 题库服务器是**唯一**不通过子进程隔离的组件，因此它崩溃会连带启动器；所有异常都在
`QuestionBankHandler` 内被捕获并转成 JSON 错误响应，不允许向上抛。

### 3.3 线程模型

| 线程 | 数量 | 创建位置 | 职责 |
| --- | --- | --- | --- |
| WebView 主线程 | 1 | `webview.start()` | 事件循环；`js_api` 调用在此线程进入 |
| 核心输出读取线程 | 每核心 1 | `RuntimeProcessService` / `ProcessSupervisor` | `readline` 循环 → 解码 → 回调 |
| 延迟任务 daemon | 每任务 1（`threading.Timer`） | `ScheduledTaskService` | 启动后延迟动作、ZHS 会话检查 |
| 更新检查/安装线程 | 每次 1–2 | `UpdateController`、`LauncherUpdateService` | 网络 + 解压，结果回调回主线程 |
| 课程抓取线程 | 每账号 1 | `CourseAPIService` | 运行核心的 fetch 子进程并解析 |
| 题库 HTTP 线程 | 每请求 1 | `ThreadingHTTPServer` | `/query` 等接口 |
| 自动关机/退出线程 | 临时 | `WebActionService._exit_async` 等 | 避免在 API 调用栈内销毁窗口 |

共享状态用 `launcher._runtime_lock`（`RLock`）保护，涉及
`processes` / `running` / `starting` / `stop_requested` 四个字典与批量启动标志。
`YatoriRuntimeLimit` 复用同一把锁，保证「定时器触发」与「用户停止」不会互相踩踏。

### 3.4 状态真源（Single Source of Truth）

```
launcher.running[core]        bool   是否在跑（唯一真源）
launcher.starting[core]       bool   启动请求进行中（防重复点击）
launcher.processes[core]      Popen  当前子进程句柄
launcher.stop_requested[core] bool   用户主动停止，用于把 returncode 解释为「正常」
launcher.log_history[source]  list   每源最多 400 行，进度行可原地替换
launcher._last_start_error / _last_start_failure_kind   dict  最近一次启动失败原因
launcher._runtime_event_sequence / _last_runtime_event  递增事件号 + 最近事件
```

前端展示的 `runtime_state` 是这些字段的**只读投影**（`WebStateService`），投影失败不会
影响真源，只会让该字段降级为默认值并记入 `state_issues`。

### 3.5 一次「开始刷课」的完整链路

以天依说「帮我刷大学物理」为例：

```
app.js  tianyiAgentChat()  →  pywebview  →
WebLauncherAPI.tianyi_agent_chat(payload)
  → UnifiedLauncher.tianyi_agent_chat_from_web
    → TianyiAgentService.chat()            解析意图 + 选工具
      → 工具 resolve_course(query)          CoursePlanService 模糊匹配
      → 工具 start_course(course, core)     CourseRunService
         ├─ CourseOverlayService.begin()    暂存原配置 + 写覆盖（Autovisor：configs.ini）
         ├─ CoreLaunchService.start_autovisor()
         │    ├─ ConfigService 读取/校验 accounts
         │    ├─ AutomaticDependencyManager 必要时补依赖
         │    └─ RuntimeProcessService.start()  Popen + reader 线程
         └─ 记录 data/course_run_overlay.json（崩溃恢复用）
      ← 返回 {ok, course, core, message}
  ← 前端弹出确认卡（confirm_tianyi_action / cancel_tianyi_action）
```

单课程结束（或崩溃后下次启动）由 `CourseOverlayService.end()` /
`_recover_course_run_overlays()` 还原配置，避免把临时限制写死在用户的 `configs.ini` 里。

- 复用 `src.application_bootstrap.launch_desktop_process`；Windows 日常启动使用
  `python.exe` + `CREATE_NO_WINDOW`，不再假设 venv 的 `pythonw.exe` 必定不会拉出控制台子进程；
- 工作目录固定为项目根，UTF-8 无缓冲输出写入 `logs/launcher_startup_*.log`，
  stdin 使用 DEVNULL，不继承引导窗口的输出管道，避免引导窗口等待 GUI 全生命周期；
- 直接运行 `.py` 或旧版入口时，`main()` 在依赖检查和账号工作之前移交无控制台进程，
  父进程退出；防御标记避免重复移交，显式 `--dev` 保留终端；
- `Popen` 后最多等 1 秒确认没有立刻退出；若 1 秒内退出（包括返回码 0），
  抛 `RuntimeError("启动器在启动确认期间提前退出，返回码: …")`；
- 因此「bootstrap 成功但窗口没出现」要看 `logs/bootstrap_*.log`、`logs/launcher_startup_*.log` 与 `logs/crash_*.log`，
  而不是重跑 `--install`。

**日志与编码**

- `BootstrapLogger` 同时写控制台与 `logs/bootstrap_YYYYmmdd_HHMMSS.log`；
- `--check` 使用纯控制台 logger，**不会**创建 `logs/` 目录（保证只读语义）；
- `main()` 首先调用 `_configure_console_encoding()`：把 stdout/stderr 的
  `errors` 设为 `replace`。原因：项目路径含 `•`、`↗` 等 GBK 外字符，
  未处理时打印日志路径会抛 `UnicodeEncodeError` 而中断引导。

**退出码**：`0` 成功；`1` 失败（日志末尾会提示把 `logs` 下 bootstrap 日志发给维护者）。

> 设计约束：`bootstrap.py` 与 `src/install_sources.py`、`src/source_probe.py`
> 必须只用标准库，因为它们在 venv 建立之前就可能被执行。

### 4.3 启动器进程初始化

`统一启动器.py:1929 main()` 固定六步：

1. `install_crash_hook(base_dir)`：任何未捕获异常写 `logs/crash_*.log`
   （含时间、Type、Value、Traceback），再交给原 hook；
2. `ensure_core_dependencies(...)`：按 `src/dependencies.py` 实测导入，
   缺失则在当前解释器补装（frozen 环境跳过）；
3. 重新 `import webview`，失败抛
   `RuntimeError("Web 界面依赖 pywebview 不可用…")`；
4. `resolve_file_dialog_constants()`：兼容 pywebview 4 的枚举/常量两种形态；
5. `enable_windows_dpi_awareness()`：`shcore.SetProcessDpiAwareness(1)`；
6. `WebApplicationBootstrap(launcher_factory=UnifiedLauncher, api_factory=WebLauncherAPI, webview_module=webview).run(debug='--dev' in sys.argv)`。

`UnifiedLauncher.__init__`（`统一启动器.py:683`）的顺序是有意为之：

```text
① 初始化四张状态表：processes / log_history / running / starting / stop_requested
   （每张表都含 yatori、autovisor、practice、zhs 四个键）
② self._runtime_lock = RLock()、定时任务服务、ZHS 日志格式化器
③ LauncherStartupService.compose()
     DesktopPlatformService → PreferencesService（带副作用/回滚注入）
     → 题库控制器 → Autovisor 依赖管理器 → CoreManager → UpdateController
④ _recover_course_run_overlays()   # 上次异常退出残留的单课程覆盖
⑤ log_system("统一启动器已就绪")
⑥ schedule_deferred_tasks()        # 600/1000/1400/3000ms 四个延迟任务
```

| 延迟 | 任务 | 失败可见性 |
| --- | --- | --- |
| 600ms | `auto_start_if_enabled()`：按 `qb_config.json` 的 `auto_start` 起题库 | 写系统日志 |
| 1000ms | `auto_check_cores()`：自动检查三核心更新 | 只在有新版本时提示 |
| 1400ms | `_apply_auto_run_preference()`：`autoRun` 为一键启动 | 写系统日志 |
| 3000ms | `_auto_prepare_zhs_runtime()`：ZHS 环境自愈 | 写系统日志 |

### 4.5 关停流程

关停是启动器最容易出错的地方，逻辑集中在 `on_closing(confirmed=False)`
（`统一启动器.py:1896`），按顺序判断：

| 顺序 | 条件 | 行为 |
| --- | --- | --- |
| 1 | `minimizeToTray` 且未确认 | 最小化窗口继续运行，不退出 |
| 2 | 未确认且窗口可用 | 交给 `WebWindowController.request_exit_confirmation()`，由前端弹确认 |
| 3 | 有 yatori/autovisor/practice 在跑且未确认 | 取消关闭 |
| 4 | — | 取消延迟任务、Yatori 限时定时器、待执行关机 |
| 5 | 有核心任务 | `stop_all()`（含题库）；否则只 `course_api.stop_active_fetch()` |
| 6 | 题库在跑 | `stop_question_bank()` |
| 7 | 存在已下载待应用的启动器更新 | 先启动 `应用更新.cmd`（500ms 后关闭本进程） |
| 8 | — | `web_window_controller.close_window()` |

`exit`（页内退出按钮）走同一个 `on_closing()` 让用户看到确认框；
`exit_app` 是「已确认退出」，在后台线程直接 `on_closing(confirmed=True)`，
避免与 pywebview 销毁窗口的时机竞争。

### 5.8 题库域

#### `src/题库服务器.py`（1348 行）

本地 HTTP 题库服务，Autovisor 与 Yatori 通过 `POST /query` 查询答案。

**查询流水线**（`_handle_query` :1083）：

```text
title+options
  → ① 内置 ZError 题库（SQLite，_query_zerror_db）
  → ② 本地缓存（data/题库缓存.db，query_local）
  → ③ 远程 ZError（QB_REMOTE_URL + QB_REMOTE_TOKEN，8 秒超时）
  → ④ AI 兜底（_call_ai，按 _ai_config 逐模型调用）
  → 统一响应 {success, data:[{id,question,answer,is_ai,is_pending_correction,source}]}
```

**接口表**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST | `/query` | 参数 `title`、`options`（分隔符兼容） |
| GET | `/api/status` | 运行状态、统计、匹配配置 |
| POST | `/api/clear_cache` | 清空缓存 |
| GET | `/api/export` | 导出 JSON |
| POST | `/api/import` | 导入题目 |
| GET | `/api/statistics` | 题量/命中统计 |
| POST | `/api/deduplicate` | 去重 |

**匹配算法**：`_normalize`（全角/标点归一）→ `_extract_keywords`（jieba，
去 `QUERY_STOPWORDS`）→ `_keyword_coverage` + `_char_similarity` →
`_compute_match_score` 加权。题干含「以下/下列/下面/下叙」时
（`QUESTION_OPTIONS_MATCH_KEYWORDS`）必须同时匹配选项，
避免同题干不同选项的题被串答案。阈值由 `configure_match()` 设置：
相似度阈值、关键词覆盖率下限、字符相似度快速通过线。

**URL 处理**：`_extract_urls`/`_normalize_urls` 会把题干里的链接抽出来单独比对，
因为同一道题在不同课程页面的 URL 参数可能不同。

- 工具调用提示词与旧文本 CMD 提示分离；前端最多携带最近 6 条历史，旧消息最多 1200 字符，
  人格最多 1800 字符；后端另限制最近 8 条消息、历史总计 6500 字符及系统人格 2400 字符。
  最新用户消息最多 3000 字符，超长请求要求拆分，不静默截掉操作后半段。
- 按本轮意图筛选工具；`get_settings.paths` 可只取指定字段/分组，返回模型的数据按列表条数、
  字符数和层级压缩，并提示截断。只读工具在单次请求内按参数缓存，跨请求重新读取。
- 已明确返回不支持工具调用的模型配置缓存 5 分钟，避免反复探测后再回退；网络错误不缓存。
  文本回退仅可自动查询状态或跳转页面，不能绕过确认执行写操作。
- 本地基准：设置请求的工具说明序列化长度约减少 44%；30 条超长历史的压力样例请求体约减少 96%。
  这是字符数比较，不是实际服务商计费 Token、费用或自然语言准确率统计。

### 6.1 硬性约束（改前端前必读）

## 7. Autovisor（自研刷课核心）

Autovisor 是项目里唯一「完全可控」的核心：Python + Playwright，能被启动器
注入参数、能被单测覆盖、也能被临时改配置。

### 7.1 三个入口

| 入口 | 参数 | 用途 |
| --- | --- | --- |
| `Autovisor/Autovisor.py` | `--config/-c`、`--account-id`、`--course-url` | 单账号；启动器最常用 |
| `Autovisor/Autovisor_Multi.py` | `--max/-m`、`--example`、`--list` | 多账号并发 |
| `Autovisor/Practice_Mode.py` | — | 练习模式（只刷题不看视频） |

每个入口第一行都调用 `activate_runtime_dependencies()`
（`Autovisor/runtime_bootstrap.py:9-21`），把项目根与 `runtime_deps/`
插到 `sys.path[0]`。这是 Autovisor 的「非 pip 依赖」机制：
`numpy`/`opencv` 的 wheel 被解压进 `Autovisor/runtime_deps/`，
不污染启动器 venv。

### 7.2 启动链

```text
Autovisor.py:857  _parse_args()
  → run()                                  :804-854
      → Logger().configure()
      → Config(config_path, account_id)    读 configs.ini
      → --course-url 覆盖 course_urls
      → asyncio.run(main())
          → enableAutoCaptcha ? installer.start() : 跳过   :744-801

          → init_page()                    :90-116

          → run_with_task_guard(run_course_queue)
```

`init_page` 的细节值得注意：`chromium.launch(channel=driver, headless=False,
executable_path=EXE_PATH, args=["--window-size=…", "--window-position=100+account_offset*80"])`，
再用 `add_cookies("res/cookies_N.json")` 恢复登录态。窗口偏移量按账号号递增，
多开时窗口不会完全重叠。

**退出码语义**：`run()` 按异常类型分类
（`TargetClosedError`、`KeyError`、`FileNotFoundError`、`UnicodeDecodeError`、
`CourseAuthenticationError`）。启动器据此决定「登录失效」还是「临时崩溃」，
前者不自动重试，后者会记入 `failureKinds`。

### 7.3 多账号

`Autovisor_Multi.py` → `MultiAccountManager.run_all(max_concurrent)`
（`modules/multi_account_runner.py:61`）：

**学习循环**（`Autovisor.py:229-571`）：

| 参数 | `--config`、`--account-id`、`--course-url` | 无参数 | `play/homework/exam/fetch` + `-c` |
| 配置 | `Autovisor/configs.ini` | `Yatori/config.yaml` | `data/zhs/account-<id>/.zhs/config.toml` |
| 登录态 | `res/cookies_N.json` | 内置 | `.zhs/cookies.json` |
| 题库接入 | 环境变量 `QB_URL` | `apiQueSetting.url` | `[question_bank].query_url` |
| 安装/更新 | 只检查，禁止覆盖 | 同盘目录替换 | tag 归档 + 哈希清单 + 备份 |
| 日志源 | `Autovisor/logs/*.txt` | 进程 stdout | 进程 stdout（JSON/文本混合） |
| 失败语义 | 异常类型分级 | 返回码 | 验证码中断 + `_zhs_run_had_failure` |

### 10.2 一个核心必须实现的五个契约

`CoreLaunchService` 把三核心收进同一套流程，任何新核心都要满足：

| 契约 | 对应实现 | 说明 |
| --- | --- | --- |
| ① 构造命令 | `_get_yatori_command()` / `build_autovisor_runtime_env()` / `ZhsService.build_command()` | 只返回 argv 与环境，不负责起进程 |
| ② 环境就绪 | `AutovisorDependencyManager`、`ensure_zhs_runtime`、`prepare_autovisor_question_bank` | 起进程前把依赖/题库/配置准备好 |
| ③ 状态位 | `running[core]` / `starting[core]` / `stop_requested[core]` | 由 `ProcessSupervisor.claim_start` 加锁维护 |
| ④ 日志源 | `log("yatori"|"autovisor"|"zhs", line)` | 统一进 `log_history`，每源 400 行 |
| ⑤ 退出语义 | `RuntimeCoordinator.handle_runtime_exit()` | 决定「正常结束 / 失败 / 用户停止」，进而决定关机 |

新核心如果绕过这五条，前端状态卡会显示不出来、关机逻辑也会误判。

### 10.3 课程域的五段式协作

```text
课程清单    CourseCatalogService   抓取 + 30 分钟缓存 + 身份绑定
   ↓ 候选课名
课程解析    CoursePlanService      NFKC 归一 + 完全匹配(1.0) 或 长度比加权(0.5+0.4*ratio)
   ↓ {core, name, key}
课程决策    CourseRunService       resolve_smart：只读缓存优先，必要时才拉课程
   ↓
临时覆盖    CourseOverlayService   写 marker → 改配置（YAML/INI）
   ↓
启动与还原  RuntimeProcessService + RuntimeCoordinator
```

**为什么要有 `resolve_smart`**：拉课程要起浏览器/登录，代价高。
用户第二次刷同一门课时应该直接用缓存命中，只有缓存里没有才重新拉取。

**为什么覆盖要先落 marker**：崩溃场景下，内存里的原值已经丢了，
只有磁盘上的 `data/course_run_overlay.json` 能让下次启动还原配置。

### 10.4 失败分类与提示

`RuntimeCoordinator` 把失败归入 `failureKinds`，前端据此给出不同文案：

| 来源 | 典型 failureKind | 用户提示方向 |
| --- | --- | --- |
| 配置缺失/非法 | 配置类 | 去「核心设置」补账号或课程 |
| 依赖缺失 | 依赖类 | 跑 `bootstrap.py --install` |
| 登录失效 | 认证类 | 重新扫码/改密码，不要重试 |
| 浏览器/驱动缺失 | 环境类 | 装 Chrome/Edge 或 Playwright |
| 进程崩溃 | 运行类 | 看日志，可重试 |
| 验证码 | 人工类（仅 ZHS） | 去验证页面，验证后继续 |

`start_all` 会把这些一次性返回：`{ok:false, message, failureKinds}`，
前端按第一个失败项决定主提示，其余进详情。

### 10.5 题库的三种接入方式

| 核心 | 接入点 | 谁写入 |
| --- | --- | --- |
| Yatori | `setting.apiQueSetting.url` | `_sync_yatori_question_bank_url()` |
| Autovisor | 环境变量 `QB_URL` | `build_autovisor_runtime_env()` |
| ZHS | `[question_bank].query_url` | 用户在 ZHS 设置页填写 |

三者互不影响：关掉本地题库服务器时，Yatori/Autovisor 会查询失败
（Autovisor 会重试 5 次后放弃该题），ZHS 则继续用自己的远程题库。

### 10.6 一次「一键启动」的时序

```text
前端 perform_action('start_all')
  → WebActionService → UnifiedLauncher.start_all()
    → RuntimeCoordinator.start_all()                       :241
        ├─ 抢 _batch_lock（非阻塞；失败 → "一键启动正在进行中"）
        ├─ prepare_start("batch")                          取消待执行关机
        ├─ 空闲轮次 → reset_failures_for_new_round()
        ├─ 读取 batchTargets；未选目标 → 明确返回，不启动题库
        ├─ 已运行目标跳过；未配置/未安装目标写入 skipped
        ├─ 仅待启动的 Yatori / Autovisor 需要题库时，静默启动题库
        ├─ 对其余可运行的所选目标调用 start_yatori / start_autovisor / start_zhs
        └─ failures 非空 → mark_batch_failed() → 返回 {ok:false, failureKinds}
  ← 返回 {ok, message, toast, toastType, submitted, skipped, alreadyRunning}
```

软件设置的「一键启动目标」同时作用于按钮、`autoRun` 和 Agent 的 `start_all`。
默认保留旧版的 Yatori / Autovisor，ZHS 可勾选加入。按钮使用已保存的核心配置，
不强制保存其他配置页中尚未提交的草稿；Agent 指定单个核心时仍按明确目标操作。

全部任务结束后由 `_finalize_if_idle()` 决定：`autoShutdown` → 60 秒倒计时
关机；`closeLauncherOnComplete` → 关闭启动器。任一核心「失败」或
「ZHS 验证码中断」都会抑制这两个动作。

### 10.7 并发与互斥规则

| 规则 | 实现 | 违反后果 |
| --- | --- | --- |
| 同一核心只能有一个进程 | `ProcessSupervisor.claim_start()` 占位 | 双击启动按钮会起两个浏览器 |
| 练习模式与正式刷课互斥 | `practice` 独立状态位 + 启动前检查 | 两个 Playwright 抢同一份 Cookie |
| 单课程覆盖同一时间只允许一轮 | overlay marker 存在则拒绝新任务 | 配置被写乱、无法还原 |
| `start_all` 只允许一个批次 | `_batch_lock` 非阻塞 | 重复提交导致重复启动 |
| 题库启停串行 | `QuestionBankController` 内部锁 + 端口探测 | 端口占用导致启动失败 |
| 设置保存串行 | 前端 `settingsSaveTail` + 后端 `RLock` | 并发写配置互相覆盖 |

| 规则 | 位置 | 行为 |

| 题库端口 1024–65535 | `web_settings_service._prepare_payload` | 非法返回 `{ok:false}` |
| Autovisor 速度取值 | `config_service.normalize_autovisor_speed` | 归一到合法档位 |
| Autovisor 账号数 > 1 | `web_settings_service._normalize_autovisor` | 强制 `multi_mode` |

| ZHS threshold/速度 | `zhs_service._normalize_settings` | threshold 0–1，速度 1.0–2.0 |

### 11.8 保存事务

三组配置一次保存（`save_settings`）是**跨文件事务**：

```text
capture_file_state(三份文件)
  → 写 Yatori/config.yaml
  → 写 Autovisor/configs.ini
  → 写 multi_mode（可能同时改 INI）
  → 写 data/qb_config.json（可能重启题库）
  → 任一失败：restore_file_state() + 回滚 multi_mode → {ok:false, message}
```

因此「保存到一半断电」不会留下半份配置：要么全改，要么全回滚。

| Yatori 更新回滚 | 同盘替换失败 | `os.replace` 反向 | 自动 |
| ZHS 更新备份 | ZHS 更新 | `zhs-backup-<时间戳>/` | 失败自动换回 |

### 12.5 敏感数据

| 数据 | 位置 | 风险 |
| --- | --- | --- |
| 平台账号密码 | `Yatori/config.yaml`、`Autovisor/configs.ini` | 高（明文） |
| AI API Key | `qb_config.json`、偏好 `tianyiAi`、ZHS `config.toml` | 高 |
| Cookie | `Autovisor/res/cookies_*.json`、`.zhs/cookies.json` | 高（可直接登录） |
| 题库令牌 | `QB_REMOTE_TOKEN` 环境变量 | 中 |

规则：

1. 这些文件**永远不进 Git、不进发布包**（构建脚本已用白名单+`PRIVATE_*` 处理）；
2. 写文档/示例/截图时一律用占位符；
3. 日志脱敏由 AI 服务负责，新增日志时不要打印完整 Key/Cookie；
4. 若曾提交过，按「轮换凭据 → 从索引移除 → 通知使用者」处理，
   仅删文件不足以清除历史。

### 12.6 发布包里的隐私边界

`scripts/build_launcher_release.py` 的排除规则：

```text
PRIVATE_NAMES    = {config.yaml, configs.ini, qb_config.json,
                    launcher_preferences.json, cookies.json}
PRIVATE_SUFFIXES = {.db, .sqlite, .sqlite3, .log, .bak, .secret}
EXCLUDED_DIRS    = {__pycache__, .pytest_cache, node_modules, .git, .venv,
                    data, logs, log, output, uploads, attachments, screenshots, .dsh}
EXCLUDED_PATHS   = {zhs/config.toml, zhs/.venv}
```

改构建脚本时，任何新增的「运行期数据目录」都要同步加进 `EXCLUDED_DIR_NAMES`，
否则用户更新后会把自己的数据打包进发布包。

## 15. 构建与发布

### 15.1 两种产物

| 产物 | 脚本 | 内容 | 用途 |
| --- | --- | --- | --- |
| `launcher-<version>.zip` | `scripts/build_launcher_release.py` | 启动器本体（`统一启动器.py`、`src/`、`web/`、`zhs/`、两个 requirements） | 增量自更新 |
| `shuake-toolkit-<version>.zip` | `scripts/build_full_release.py` | 全量包（含 `Autovisor/`、`Yatori/`、`scripts/`、`docs/`） | 首次安装 / 完整分发 |

两者都附带 JSON 清单：`launcher-manifest.json` / `full-manifest.json`。

### 15.2 `build_launcher_release.py`

```powershell
python scripts/build_launcher_release.py --version v1.7.3 --out dist --require-version-match
```

| 参数 | 说明 |
| --- | --- |
| `--version` | 必填，如 `v1.7.3` |
| `--out` | 输出目录，默认 `dist` |
| `--require-version-match` | 校验 `--version` 与 `统一启动器.py` 的 `LAUNCHER_VERSION` 一致 |
| `--print-json` | 只打印清单 JSON，方便 CI 读取 |

**白名单**（只打这些）：

```python
WHITELIST        = ("统一启动器.py", "requirements.txt", "bootstrap.py",
                    "requirements-zhs.txt", "src", "web", "zhs")
LEGACY_WHITELIST = ("统一启动器.py", "requirements.txt", "src", "web")
```

**排除**：

```text
EXCLUDED_DIR_NAMES   = __pycache__ .pytest_cache node_modules .git .venv
                       data logs log output uploads attachments screenshots .dsh
EXCLUDED_SUFFIXES    = .pyc .pyo
PRIVATE_SUFFIXES     = .db .sqlite .sqlite3 .log .bak .secret
PRIVATE_NAMES        = config.yaml configs.ini qb_config.json
                       launcher_preferences.json cookies.json
EXCLUDED_RELATIVE    = zhs/config.toml zhs/.venv
```

**完整性哨兵** `REQUIRED_FILES`：缺任何一个直接构建失败——

```text
统一启动器.py, requirements.txt, bootstrap.py, requirements-zhs.txt,
src/web_action_service.py, src/zhs_service.py, web/app.js,
web/现代启动器_UI_预览.html, zhs/pyproject.toml, zhs/UPSTREAM.json
```

**清单字段**：

| 字段 | 含义 |
| --- | --- |
| `version` / `asset` / `size` / `sha256` | 包信息 |
| `files` | 文件列表 |
| `legacyFiles` | 旧客户端可见的文件集合 |
| `fileList` | **旧客户端（≤v1.7.0）**可替换范围（`LEGACY_WHITELIST` 子集） |
| `fullFileList` | 全量排序文件列表，供 v1.7.2+ 完整性校验 |
| `replaceWhitelist` | 替换白名单，必须与代码里的常量一致 |

> **三处白名单必须完全一致**：`build_launcher_release.py` 的 `WHITELIST`、
> `src/launcher_update_service.py` 的 `REPLACE_WHITELIST`、清单里的
> `replaceWhitelist`。改一处不改另外两处，会导致「下载成功但替换被拒」。

### 15.3 `build_full_release.py`

```powershell
python scripts/build_full_release.py --version v1.7.3 --out dist --require-version-match `
  --yatori-core-url <url> --yatori-core-sha256 <sha> --yatori-core-size <bytes> --yatori-core-version v2.6.2-beta.8
```

- 包含 `ROOT_FILES` / `ROOT_DIRS` 定义的全量内容；
- `EXCLUDED_SUFFIXES = {.pyc, .pyo, .exe, .zip}` 排除原目录里的历史二进制；
  构建时通过 `scripts/build_desktop_entry.py` 从 C# 源码编译带图标的 `统一启动器.exe`，
  单独加入 ZIP 和完整性清单。默认需 Windows .NET Framework 编译器；
  非 Windows 可用 `--desktop-exe <路径>` 引入已编译的 Windows 入口。
  Yatori 可执行核心仍通过 `--yatori-core-*` 参数引用外部下载地址；
- 产出 `shuake-toolkit-<version>.zip` + `full-manifest.json`。

### 15.4 更新兼容性

`launcher-manifest.json` 要同时服务两代客户端：

- **≤ v1.7.0**：只认 `fileList`，不了解 `fullFileList`；
- **≥ v1.7.2**：用 `fullFileList` + `replaceWhitelist` 做逐文件校验。

所以新增「启动器文件」时：

1. 加进 `WHITELIST`；
2. 判断是否需要旧客户端也能替换——需要则同时进 `LEGACY_WHITELIST`；
3. 同步 `REPLACE_WHITELIST`；
4. 若是「完整性哨兵」，加进 `REQUIRED_FILES`。

### 15.5 CI 工作流

`.github/workflows/release-launcher.yml`（108 行，唯一工作流）：

| 项 | 值 |
| --- | --- |
| 触发 | push tag `v*`；或 `workflow_dispatch`（`version` 必填） |

| 运行器 | `windows-latest` + Python 3.13，脚本步骤使用 Bash |

```text

```

构建前置检查为完整 pytest 与 `node --check`；JUnit 报告作为工作流附件保存。
这些检查不能代替真实账号与第三方平台验收。

### 15.6 发布前检查清单

1. 修改 `统一启动器.py` 的 `LAUNCHER_VERSION`（启动器发布版本）；
   内部包版本及第三方核心版本按各自变更维护，不强制与启动器同号；
2. 更新 `docs/releases/<tag>.md`，记录本次全部内容，不再向 HTML 写日志；
3. 发布流程用该 Markdown 作为 GitHub Release 说明；关于页联网读取最新已发布版本；
4. `node --check web/app.js`；
5. 本地跑 `python -m pytest`（至少 `test_about_changelog`、
   `test_launcher_update_service`、`test_build_*`）；
6. `build_launcher_release.py --require-version-match`；
7. `build_full_release.py`；
8. 校验 manifest 的 `size` / `sha256` / `fileList`；
9. 解压检查**不含** `config.yaml`、`configs.ini`、`cookies*.json`、
   `data/`、`zhs/config.toml`；
10. 打 tag 推 CI。

### 15.7 版本号规则

| 版本 | 位置 | 当前值 | 谁读它 |
| --- | --- | --- | --- |
| 产品版本 | `src/version.py` | `3.0.0` / `2026-05-27` | 关于页展示 |
| 启动器版本 | `统一启动器.py` 的 `LAUNCHER_VERSION` | `v1.7.3` | 自更新比较、构建校验、本地版本展示 |
| Yatori 版本 | `.core_versions.json` | `v2.6.2-beta.11` | 核心状态卡 |
| Autovisor 版本 | `.core_versions.json` | `null`（本地魔改版） | 核心状态卡 |
| ZHS 版本 | `zhs/UPSTREAM.json` | `0.1.5` | ZHS 面板 |

两套版本并存是历史原因，**发布只认 `LAUNCHER_VERSION`**。

### 15.8 发布之后

用户端自更新链路（详见 `docs/更新指南.md`）：

```text
客户端检查 Release → 下载 zip + manifest
  → 校验 size / SHA-256（失败保留旧文件）
  → 解压到 .update-staging/
  → 拉起 .update-staging/应用更新.cmd 并退出启动器
  → 脚本等旧进程退出 → 备份到 .update-backup/ → 替换白名单 → 逐文件 fc /b
  → 失败回滚 → 成功后 bootstrap.py --prepare-zhs --quiet → 重启
```

如果发布的是「坏包」，由于 `fc /b` 逐文件校验 + 备份存在，
用户最坏情况是回到旧版本，而不是变砖。

### 16.2 新代码放哪里

| 你要做的事 | 放哪 |
| --- | --- |
| 新的业务能力 | 优先放入现有领域模块；确需独立职责时新增 `src/<domain>_service.py`，按使用时机选择启动装配或惰性 getter |
| 给前端暴露接口 | `src/launcher_api.py` 加薄转发，在 `统一启动器.py` 增加门面方法并委托对应服务 |

### 16.3 约定

- **日志用中文**，面向用户；异常信息也要能直接看懂；
- 操作型后端方法捕获异常并返回 `{ok, message}`；查询接口按各自状态契约返回，不强制包装成同一结构（见 §13.2）；
- 新增文件写清 docstring（模块职责 + 关键约定），现有模块都这么写；
- 不要引入新的第三方依赖；确实需要时改 `src/dependencies.py`
  并同步 `requirements.txt`（有测试校验一致性）；
- 不要在前端引 CDN；不要给 `app.js` 加框架/构建步骤。

### 16.4 改动自检清单

- [ ] `python -m pytest` 通过（至少改动相关的文件）；
- [ ] 前端改动的函数名/变量名没有破坏字符串契约测试；
- [ ] 新增 `apiCall` 已在 `WebLauncherAPI` 有同名方法；
- [ ] 改配置字段时同步了 `config_service`、`web_settings_service`、前端三处；
- [ ] 新增「启动器文件」时同步了 `WHITELIST` / `REPLACE_WHITELIST` / `REQUIRED_FILES`；
- [ ] 没有把 `data/`、`logs/`、`config.yaml`、Cookie 打进产物；
- [ ] 涉及版本号时两个版本号都考虑过。

### 16.5 常见改造场景

**加一个配置项**

```text
① src/preferences_service.DEFAULT_PREFERENCES 或 config_service
② src/web_settings_service（校验/合并）
③ 统一启动器.py 的 get/save_web_preferences 转发
④ web/app.js 的 normalizeSettings / 渲染 / 保存 payload
⑤ tests/test_*_frontend.py 补断言
```

**加一个按钮动作**

```text
① web_action_service.perform() 加分支
② 后端实现方法（返回 {ok, message}）
③ 前端 perform_action 调用 + 结果处理
④ 若动作有副作用（启动/停止），走 RuntimeCoordinator 而不是直接起进程
```

**加一个核心**

```text
① 实现五个契约（命令/环境/状态位/日志/退出语义）
② CoreManager 加下载与校验（若需要更新）
③ 状态服务加字段（web_state_service.runtime_state）
④ 前端加状态卡与设置页
⑤ 更新白名单与构建清单
```

## 17. 排障 FAQ

### 17.1 启动与界面

**双击没反应 / 闪退**

看 `logs/` 下最新的 `crash_*.log` 与 `bootstrap_*.log`。
常见原因：Python 版本不在 3.11–3.13、依赖没装全、WebView2 缺失。

**窗口白屏**

1. 确认 `python -m webview` 可用（`pywebview` 已装）；
2. 用 `--dev` 启动看控制台报错；
3. 检查 `web/现代启动器_UI_预览.html` 是否被误删（`REQUIRED_FILES` 之一）。

**提示「Web 界面依赖 pywebview 不可用」**

`py -3 bootstrap.py --install` 重装依赖；或检查是否在错误的 venv 里启动。

**清空日志**：界面「清空日志」只清内存；磁盘日志在 `logs/`，
或开启偏好 `autoCleanLogs` 自动清 7 天前文件。

### 17.2 依赖与安装

**pip 安装超时**

`bootstrap.py` 会并发测速选镜像（清华/阿里/华为/官方），失败自动降级。
仍失败时设环境变量禁用代理逻辑：`LAUNCHER_ALLOW_GITHUB_PROXIES=0`，
或手动 `pip install -r requirements.txt -i <镜像>`。

**Playwright 报 `EPERM mkdtemp`**

工作区文件带 Low 完整性标签，浏览器进程无法创建临时目录。修复：

```powershell
icacls "." /setintegritylevel Medium /t /c /q
```

**explorer 打不开报 `0xc0000142`**

同上，用带引号的继承版本：

```powershell
icacls "." /setintegritylevel "(OI)(CI)Medium" /t /c /q
```

### 17.3 核心相关

**Yatori 启动即退出**

`config.yaml` 的 `users` 为空或字段缺失；启动器会先校验再起进程，
看系统日志里的具体缺项。

**Autovisor 浏览器没起来**

1. 系统 Chrome/Edge 是否安装；
2. `--check` 是否提示 Playwright 浏览器缺失；
3. `Autovisor/runtime_deps/` 是否存在（`numpy`/`opencv`）。

**ZHS 提示「依赖不完整」**

跑 `bootstrap.py --prepare-zhs`。ZHS 需要 Python 3.13/3.14，
与启动器的 venv 相互独立（`.runtime/venv-zhs`）。

**ZHS 扫码后仍要求登录**

`cookies.json` 缺 `CASTGC`/`SESSION`/`SERVERID` 之一，或已过期。
用「刷新会话」强制服务端校验；仍失败则清除登录重扫。

**ZHS 刷课停在验证码**

日志出现 `captcha required (racId=…)` 时，点 ZHS 卡片的「去验证」，
在浏览器完成验证后回到启动器继续。此时即使进程返回 0 也不会自动关机。

**课程列表为空 / 找不到课程**

课程缓存 30 分钟；点「刷新」强制拉取。学习通账号需先在 Autovisor
设置里登录并保存 Cookie。

### 17.4 更新

**更新后提示版本没变**

自更新在**退出启动器**时才应用；更新成功后启动器会自动重启。
如果核心任务在跑，会推迟到任务结束。

**更新失败**

`.update-backup/` 里有完整备份，应用脚本失败会自动回滚。
手动恢复：把 `.update-backup/<时间戳>/` 内容拷回项目根。

**ZHS 更新报「本地有改动」**

`zhs/` 与 `UPSTREAM.sha256` 不一致（有人改过源码）。确认要覆盖后用
`python scripts/update_zhs.py --force`。

**Autovisor 显示有新版但不能更新**

设计如此：Autovisor 含本地适配，启动器只检查版本、不覆盖安装。

### 17.5 其他

**点了「全部完成关机」但没关机**

任一核心失败或 ZHS 验证码中断都会抑制关机（防止误关）。
看系统日志的失败原因；也可用「取消关机」按钮。

**同一个核心起了两个浏览器**

说明绕过了 `claim_start` 互斥（例如双击两次启动）。
重启启动器可恢复状态；这也是为什么所有启动都要走 `RuntimeCoordinator`。

**想彻底重置**

删除 `data/launcher_preferences.json`（偏好）、`data/qb_config.json`（题库）、
`Autovisor/res/cookies*.json`（登录态）、`.runtime/venv-zhs`（ZHS 环境），
再跑一次 `bootstrap.py --install`。**不要删** `Yatori/config.yaml`，
除非你准备好重新填账号。

### 18.5 四项调整后的接口约定

- `batchTargets`：软件设置中的三核心目标列表，默认保留旧版两个核心；按钮、自动运行、
  Agent 的 `start_all` 复用 `RuntimeCoordinator.start_all()`，预检使用 `CoreLaunchService.batch_skip_reason()`。
- `core_environment`：运行状态中的 `zhs` / `autovisor` 环境摘要，包含 `phase/message/detail`。
  ZHS 的 `prepare_zhs_environment` 动作只准备环境；旧智慧树重试入口明确为「重试启动」。
  准备状态保存在当前启动器进程内，重启后重新检查；环境校验异常也必须报告失败。
- `last_launcher_update`：由 `src/launcher_update_receipt.py` 读取持久回执生成的结果。
  `open_launcher_update_log`、`dismiss_launcher_update_result` 只操作当前 ID 的记录。
  外部脚本通过独立的 PowerShell 编码命令原子写 JSON，不依赖正在替换的 `src/`。
- 发布回归：工作流完整 pytest 与 JS 语法检查是构建前置条件；报告上传不能绕过失败结果。
  本地完整检查不等同于已触发 GitHub 发布。
